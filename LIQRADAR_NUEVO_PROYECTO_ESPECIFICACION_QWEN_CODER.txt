LIQRADAR - ESPECIFICACIÓN MAESTRA PARA CREAR EL PROYECTO DESDE CERO
===================================================================

OBJETIVO
--------
Construir desde cero una aplicación profesional de análisis de mercado para BTC
orientada principalmente a futuros/perpetuos, liquidaciones, Open Interest,
funding, order flow, CVD, profundidad L2, posicionamiento de Top Traders,
clusters de liquidación, opciones y contexto multi-exchange.

IMPORTANTE:
Este documento es una especificación de arquitectura + producto + reglas de
datos + criterios de validación. NO asumir que el código heredado funciona.
La aplicación nueva debe construirse limpia, modular y testeable.

El objetivo NO es crear un "indicador que adivine el precio".
El objetivo es construir un RADAR DE EVIDENCIA que:
- consuma datos reales;
- indique qué fuente está viva;
- diferencie observación de estimación;
- detecte eventos;
- determine un régimen de mercado;
- genere LONG / SHORT / NO TRADE;
- explique la señal;
- registre qué pasó después;
- permita validar estadísticamente si la herramienta aporta valor.

===================================================================
1. PRINCIPIOS NO NEGOCIABLES
===================================================================

1) MODO REAL NO PUEDE INVENTAR DATOS.
2) Si falta un dato crítico, el sistema debe degradarse o emitir NO TRADE.
3) Nunca presentar una estimación como observación real.
4) Nunca llamar "ballena" a algo que no identifique explícitamente una cuenta.
5) Nunca llamar "spoof confirmado" a una inferencia de order book.
6) Nunca llamar "liquidación futura real" a un liquidation cluster estimado.
7) Nunca permitir que NaN, Infinity, undefined o null contamine el motor.
8) LONG siempre significa dirección alcista.
9) SHORT siempre significa dirección bajista.
10) SHORT SQUEEZE es un mecanismo alcista.
11) LONG SQUEEZE es un mecanismo bajista.
12) NO TRADE es una salida válida y necesaria.
13) No usar "19 indicadores" como 19 votos independientes.
14) Agrupar features correlacionados para evitar double counting.
15) La confidence debe poder validarse contra resultados reales.
16) Toda feature debe tener provenance.
17) Todo endpoint externo debe tener timeout/retry/circuit-breaker.
18) Las API keys nunca deben estar en el frontend.
19) Ninguna API privada debe habilitar trading/retiros para este proyecto.
20) El build debe verificarse antes de declarar el proyecto terminado.

===============================================================

Toda fuente debe normalizar a tipos comunes.

Ejemplo:

type DataTruth = "REAL" | "ESTIMATED" | "FALLBACK" | "UNAVAILABLE";

type Provenance = {
  truth: DataTruth;
  source: string;
  fetchedAt: number;
  ageMs: number;
  latencyMs?: number;
  quality: number;
  error?: string;
};

Toda feature debe poder llevar:

{
  value,
  direction,
  strength,
  confidence,
  provenance
}

Ejemplo:

{
  value: 0.83,
  direction: "bullish",
  strength: 0.77,
  provenance: {
    truth: "REAL",
    source: "binance_futures",
    ...
  }
}
